Implementation Instructions for Replit Agent
Below is a staged set of instructions. Each stage is independently deployable and independently revertible. Do not combine stages into a single commit. After each stage, run the verification steps before proceeding.

Before writing any code, perform these checks and report back:

Confirm the pg_trgm extension is installed: SELECT * FROM pg_extension WHERE extname = 'pg_trgm';. If not present, install it: CREATE EXTENSION IF NOT EXISTS pg_trgm;.

Stage 1: Search Telemetry
Goal: Log every search event so all subsequent ranking changes can be evaluated against real data. This stage must ship before any ranking changes.

1.1 Schema
Create a migration file migrations/NNNN_search_telemetry.sql with:

sql
CREATE TABLE search_event (
  id              bigserial PRIMARY KEY,
  ts              timestamptz NOT NULL DEFAULT now(),
  user_id         uuid NULL,
  session_id      text NULL,
  query_raw       text NOT NULL,
  query_normalized text NOT NULL,
  query_source    text NOT NULL CHECK (query_source IN ('typed','barcode','photo','voice','chip')),
  filters_json    jsonb NOT NULL DEFAULT '{}'::jsonb,
  results_count   integer NOT NULL,
  top_result_id   uuid NULL,
  latency_ms      integer NOT NULL,
  layers_hit      text[] NOT NULL DEFAULT '{}',
  ab_bucket       text NULL
);

CREATE INDEX idx_search_event_ts ON search_event (ts DESC);
CREATE INDEX idx_search_event_query ON search_event (query_normalized);
CREATE INDEX idx_search_event_user ON search_event (user_id, ts DESC);

CREATE TABLE search_event_click (
  id              bigserial PRIMARY KEY,
  search_event_id bigint NOT NULL REFERENCES search_event(id) ON DELETE CASCADE,
  ts              timestamptz NOT NULL DEFAULT now(),
  result_id       uuid NOT NULL,
  result_rank     integer NOT NULL,
  action          text NOT NULL CHECK (action IN ('view','add_to_list','scan_confirm','dismiss'))
);

CREATE INDEX idx_search_event_click_event ON search_event_click (search_event_id);
CREATE INDEX idx_search_event_click_result ON search_event_click (result_id, ts DESC);

1.2 Middleware
Create server/search/telemetry.ts with two exported functions:

logSearchEvent(params): Promise<bigint> — inserts a row, returns the new id. Called by the search endpoint after results are assembled but before the response is sent. Must not block the response on failure; wrap the insert in a try/catch and log errors to stderr.
logSearchClick(searchEventId, resultId, resultRank, action): Promise<void> — inserts into search_event_click.
The search endpoint must:

Capture performance.now() at entry.
After results are assembled, compute latency_ms, collect which layers produced hits into layers_hit (array of strings like 'exact_catalog', 'fts', 'trigram', 'vendor_boost').
Return the search_event_id in the response body as _telemetry.searchEventId.
The client must:

Store the returned searchEventId alongside the rendered result list.
On any result interaction (tap to view detail, add to list, scan confirm), POST to /api/search/click with { searchEventId, resultId, resultRank, action }.
1.3 Normalization function
Create server/search/normalize.ts exporting normalizeQuery(raw: string): string. Rules:

Trim and collapse internal whitespace to single spaces.
Lowercase.
Apply unaccent-equivalent in JS (use raw.normalize('NFKD').replace(/\p{Diacritic}/gu, '')).
Do not strip hyphens or slashes at this stage (catalog numbers need them).
Do not expand synonyms at this stage.
Use this function for both the query_normalized column and as the first step of search query processing. One function, two callsites.

Stage 2: FTS Weight Classes and Score Floor Removal
Goal: Replace the uniform-weighted tsvector and the + 0.4 score floor with native PostgreSQL weight classes.

2.1 Schema
Migration migrations/NNNN_fts_weighted.sql:

sql
-- Drop the existing search_tsv column and its index if present.
-- (Replace <existing_index_name> with the actual name from \d inventory.)
DROP INDEX IF EXISTS idx_inventory_search_tsv;
ALTER TABLE inventory DROP COLUMN IF EXISTS search_tsv;

-- Add a generated tsvector column with weight classes.
ALTER TABLE inventory
ADD COLUMN search_tsv tsvector
GENERATED ALWAYS AS (
  setweight(to_tsvector('simple',  coalesce(catalog, '')),                              'A') ||
  setweight(to_tsvector('simple',  coalesce(vendor,  '')),                              'B') ||
  setweight(to_tsvector('english', coalesce(description, '')),                          'C') ||
  setweight(to_tsvector('english', coalesce(array_to_string(ai_keywords, ' '), '')),    'D')
) STORED;

CREATE INDEX idx_inventory_search_tsv ON inventory USING GIN (search_tsv);

Important: catalog uses the 'simple' dictionary. English stemming must not touch catalog numbers. If catalog is nullable, the coalesce prevents generation failures.

If ai_keywords is not text[] but jsonb, replace array_to_string(ai_keywords, ' ') with jsonb_path_query_array(ai_keywords, '$[*]')::text or equivalent — inspect the column type first and adapt.

2.2 Query changes
In the search service, the FTS layer must use ts_rank_cd with explicit weight coefficients:

sql
ts_rank_cd('{0.1, 0.3, 0.6, 1.0}', search_tsv, query, 32) AS fts_score

The array is {D, C, B, A} per PostgreSQL convention. These values intentionally make catalog-match (A) ten times more valuable than ai_keyword-match (D).

2.3 Blended score changes
Locate the current blending expression in the search service (the one containing * 0.6, * 0.4, + 0.4). Replace with:

ts
// Raw scores should each be in [0, 1] after normalization.
const blended = (0.65 * ftsScore) + (0.35 * trgmScore);
// No additive floor. Results with blended < 0.05 are dropped, not boosted.

Remove the 40% threshold check entirely in this stage. Replace with a minimum of 0.05 to cut noise. The telemetry from Stage 1 will tell us the right value to use here within two weeks; do not guess further now.

2.4 Normalization of raw scores
ts_rank_cd does not return values in [0, 1]. Normalize with:

ts
const normalizedFts = ftsRaw / (ftsRaw + 1);  // maps [0, ∞) → [0, 1)

pg_trgm similarity is already in [0, 1], no change needed.

2.5 Verification
Run the migration. Confirm the generated column populates for all existing rows: SELECT count(*) FROM inventory WHERE search_tsv IS NULL; should return 0.
Run EXPLAIN ANALYZE on a typical search query. Confirm the GIN index is used (look for Bitmap Index Scan on idx_inventory_search_tsv).
Run the existing search test suite. Record which tests fail. Expected: some ranking-order tests will fail because ranking has genuinely changed. Review each failure manually; do not auto-update test expectations without reviewing whether the new order is better.
Perform these manual queries and record top-3 results for each, in a file stage2_manual_results.md committed to the branch:

Report the manual results and the test-suite diff. Wait for approval.
Stage 3: Materialized Parse Columns
Goal: Move parseCatalogNumber, trade-size parsing, and attribute extraction from query time to enrichment time. Store as typed columns for indexing and filtering.

3.1 Schema
Migration migrations/NNNN_materialized_attrs.sql:

sql
ALTER TABLE inventory
  ADD COLUMN catalog_parse    jsonb   NULL,
  ADD COLUMN amperage         integer NULL,
  ADD COLUMN pole_count       smallint NULL,
  ADD COLUMN voltage          integer NULL,
  ADD COLUMN trade_size_in    numeric(6,3) NULL,
  ADD COLUMN mount_type       text NULL,
  ADD COLUMN attrs_parsed_at  timestamptz NULL;

-- Indexes sized for the query patterns we actually have.
CREATE INDEX idx_inventory_series_poles
  ON inventory ((catalog_parse->>'series'), pole_count)
  WHERE catalog_parse IS NOT NULL;

CREATE INDEX idx_inventory_amperage ON inventory (amperage) WHERE amperage IS NOT NULL;
CREATE INDEX idx_inventory_trade_size ON inventory (trade_size_in) WHERE trade_size_in IS NOT NULL;

catalog_parse shape:

json
{
  "series": "BR",
  "poles": 1,
  "amps": 20,
  "variant": null,
  "raw": "BR120",
  "parser_version": 2
}

parser_version is mandatory. Every time the parser logic changes, increment it. Re-enrichment jobs use this field to decide what to re-parse.

3.2 Parser module
Create server/enrichment/parseAttributes.ts exporting:

parseCatalog(catalog: string, vendor: string | null): CatalogParse | null
parseTradeSize(text: string): number | null — handles 1/2", 0.5 in, 12mm (convert to inches), 3/4-inch, etc.
parseAmperage(text: string): number | null — handles 20A, 20 amp, 20-amp, 20AMP.
parsePoles(text: string): number | null — handles 1P, single pole, 2-pole, DP.
parseVoltage(text: string): number | null — handles 120V, 120/240, 277v.
parseMountType(text: string): string | null — returns one of 'bolt-on', 'plug-in', 'din-rail', 'surface', 'flush', or null.
All parsers must be pure functions with unit tests. Create server/enrichment/parseAttributes.test.ts with at least 10 test cases per parser, including ambiguous inputs that must return null rather than guessing.

3.3 Backfill job
Create scripts/backfill_attrs.ts:

Selects rows in batches of 500 where attrs_parsed_at IS NULL OR (catalog_parse->>'parser_version')::int < CURRENT_PARSER_VERSION.
For each row, runs all parsers against catalog, description, and ai_keywords combined.
Updates the row with parsed values and attrs_parsed_at = now().
Logs a count of rows processed and rows where at least one field was extracted.
Is idempotent and resumable.
Run this script in a one-off task. Do not run it inline in the migration.

3.4 Enrichment pipeline integration
Locate the existing enrichment pipeline (the thing that runs after import and populates ai_keywords, enriched_at). Add a step after AI enrichment that runs the parsers and populates the new columns. attrs_parsed_at is set in the same transaction as enriched_at.

3.5 Related Sizes query simplification
Find the current "Related Sizes" chip logic in the search service. Replace whatever string-manipulation is there with:

sql
SELECT id, catalog, description, amperage
FROM inventory
WHERE catalog_parse->>'series' = $1
  AND pole_count = $2
  AND id <> $3
ORDER BY amperage NULLS LAST
LIMIT 12;

Parameters: series, poles, current item id.

3.6 Re-enrichment policy

Otherwise no.
Add prompt_version smallint to the same migration.

  notes         text NULL,
  updated_at    timestamptz NOT NULL DEFAULT now()

-- Seed with the synonyms currently hard-coded in the query-time expander.
-- The agent must locate these in the existing codebase and migrate them here.
-- Example rows:

  ('nm-b cable',     ARRAY['romex'],                          'wire'),

-- ... agent must populate all existing synonyms from the current codebase.

-- Tokens column derived at enrichment time.
ALTER TABLE inventory
  ADD COLUMN search_tokens text NULL;

CREATE INDEX idx_inventory_search_tokens_trgm
  ON inventory USING GIN (search_tokens gin_trgm_ops);

4.2 Token builder
Create server/enrichment/buildSearchTokens.ts exporting buildSearchTokens(row, synonymGroups): string. Logic:

Start with an empty set.
Add all words from description, ai_keywords, catalog, vendor.
For each synonym group where the canonical form OR any synonym appears in the collected words, add all members of that group to the set.
Join the set with spaces and return.
Note: expansion is bidirectional. If the description contains "romex", we add "nm-b cable". If the description contains "nm-b", we add "romex". This means both worker vocabularies hit the same row.

4.3 Pipeline integration
After parse-attributes step (Stage 3) runs during enrichment, run buildSearchTokens and store in search_tokens. Also update when any synonym_group is added or edited — add a trigger or a maintenance job for this.

4.4 Query changes
Remove all query-time synonym expansion code. The search path becomes:

Normalize query (Stage 1's normalizeQuery).
Run FTS against search_tsv. (Stage 2, unchanged.)
Run trigram similarity against search_tokens (not against concatenated description/vendor/etc as before).
Blend per Stage 2's formula.
Trigram query:

sql
similarity(search_tokens, $1) AS trgm_score
-- with a WHERE clause: search_tokens % $1  (uses GIN index)

4.5 Fuse.js removal
Delete the Fuse.js import, the in-process cache, the cache-refresh timer, and Layer D from the search service.
Delete the fuse dependency from package.json.
Delete any tests that specifically target Fuse behavior. Keep tests that target search behavior generically; those should still pass against the trigram path.
Before deleting, run the current search suite with telemetry logging (from Stage 1) against a week of real queries and record which queries hit Layer D as their top layer. For each, verify the new trigram path produces an equivalent or better result. If any query degrades, add it as a test case and address before deletion.

4.6 Verification
Count rows where search_tokens IS NULL after enrichment run. Should be 0.
Repeat the Stage 2 manual queries. Compare top-3 results. Specifically:
romex should now return NM-B cable items in the top 3, not miscellaneous cable items.
thin-wall should return EMT items.
Run load test: 100 concurrent searches. Compare p95 latency before/after Fuse removal. Expected: latency drops or stays flat; memory usage of Node process drops noticeably.
Report manual results, latency numbers, memory numbers. Wait for approval.
Stage 5: Structured Photo ID Contract
Goal: Replace the free-text Vision response with a structured JSON contract. Route each field to the appropriate search path. Log success rates.

5.1 Prompt
Locate the current Vision prompt. Replace with a prompt that demands this exact JSON shape:

json
{
  "catalog_guess": "string or null",
  "vendor_guess": "string or null",
  "type_guess": "string or null",
  "attributes": {
    "amperage": "integer or null",
    "poles": "integer or null",
    "voltage": "integer or null",
    "trade_size_in": "number or null",
    "color": "string or null"
  },
  "descriptive_tokens": ["array of strings"],
  "confidence": "number between 0 and 1",
  "notes": "string or null"
}

Prompt must include: "Return only valid JSON. If a field cannot be determined from the image, use null. Do not guess. confidence reflects overall identification confidence."

5.2 Response handling
Create server/photo/handleVisionResponse.ts:

Parse JSON. On parse failure, log to a new photo_id_failure table and return a generic "could not identify" response to the client.
Validate against a Zod schema. On validation failure, same as above.
Route:
If catalog_guess is non-null: try exact catalog lookup. If hit, return that single result with match_type: 'catalog_exact'.
If catalog miss or null, but vendor_guess + attributes.amperage + attributes.poles are all present: query by those fields. Return up to 5 results with match_type: 'attribute_match'.
Otherwise fall through to: concatenate descriptive_tokens into a query string and run normal search. match_type: 'descriptive'.
5.3 Telemetry
Create table:

sql
CREATE TABLE photo_id_event (
  id                bigserial PRIMARY KEY,
  ts                timestamptz NOT NULL DEFAULT now(),
  user_id           uuid NULL,
  image_hash        text NOT NULL,
  vision_raw        jsonb NULL,
  parse_ok          boolean NOT NULL,
  catalog_guess     text NULL,
  vendor_guess      text NULL,
  match_type        text NULL,
  top_result_id     uuid NULL,
  confirmed_result_id uuid NULL,
  latency_ms        integer NOT NULL
);

CREATE INDEX idx_photo_id_event_ts ON photo_id_event (ts DESC);

confirmed_result_id is populated if the user taps "yes, that's it" on the returned result. This gives us a real success rate.

5.4 Verification
Take 20 photos of items spanning breakers, conduit, wire, devices. For each:
Record the JSON returned by Vision.
Record which routing path fired.
Record whether the top result was correct.
Compute: catalog-hit rate, attribute-hit rate, descriptive-fallback rate, overall correct rate.
If parse failure rate is >5%, stop and adjust the prompt. Do not ship with a broken parser.
Report numbers. Wait for approval.
Stage 6: Classification Review Queue
Goal: Surface low-confidence AI classifications for admin review before they pollute the taxonomy.

6.1 Schema
sql
ALTER TABLE inventory_category
  ADD COLUMN reviewed_at timestamptz NULL,
  ADD COLUMN reviewed_by uuid NULL;

CREATE INDEX idx_inventory_category_review_queue
  ON inventory_category (confidence, classified_at DESC)
  WHERE source = 'ai' AND reviewed_at IS NULL AND confidence < 0.7;

6.2 Admin view
Add a page at /admin/classification-review (or equivalent route matching the existing admin URL scheme):

Lists items in the review queue, oldest first, paginated 50 per page.
Each row shows: item photo (if present), catalog, vendor, description, current category path, confidence score.
Each row has three actions: Confirm (sets reviewed_at, reviewed_by, keeps category), Reclassify (opens category picker, sets category to new value with source = 'human' and confidence = 1.0), Skip (moves to end of queue).
6.3 Verification
Queue view loads within 1s against production-size data.
Confirm and Reclassify actions update the correct columns.
After action, item disappears from queue on refresh.
Report screenshots and timing. Wait for approval.
Cross-cutting rules
No stage depends on any later stage. If Stage 3 is blocked in review, Stage 4 cannot start, but Stages 1 and 2 must already be in production.
Every stage includes rollback instructions in its PR description. For schema changes, the rollback is the reverse migration; write it at the same time as the forward migration.
Do not modify production data without a dev-copy rehearsal. The backfill jobs in Stages 3 and 4 must each be run against a clone of production and the results sampled before running against production.
Do not change test expectations to match new behavior without documenting why the new behavior is correct. Ranking tests in particular will shift; each shift must be defended in the PR description with a sample query and a reason.
Report format after each stage: a single markdown file in the PR titled STAGE_N_REPORT.md containing verification outputs, sample queries, timing numbers, and any deviations from these instructions. Deviations require explicit approval before the PR is merged.
Begin with Stage 0. Report back with the preflight results.
